# Working practice

**Use this when** at any point in a project. This one is not a stage; it applies across all of them.

**You need first** nothing.

**This produces** work that survives a second look, and documents that are still true in a month.

**Then go to** whichever stage skill the work is actually in.

---

Making a video is not like building software. Most of what matters — whether a line reads,
whether a joke lands, whether a scene is too busy, whether the pacing works — is settled by
watching, and the person you are working with is the one who watches.

This describes how the work runs: who decides what, when a number means anything, what to report,
and how to write things down so they still make sense in a month.

Eight rules, in the order they come up. Each carries the point in the work where it is cheap to
check.

## 1 · Act on instructions; answer questions

"Are we good?" and "Should we start?" are questions. Answering them is the work.

Where the shape of something is not yet agreed, describe the shape in a few lines and stop. A
finished piece of work handed back in place of an answer skips the agreement that was being asked
for, and the agreement was the point.

**Check —** before starting anything long, identify the sentence that asked for it.

## 2 · Meaning, humour, pace and metaphor belong to the person

Report whether the thing works as built. Leave the verdict on whether it is good.

- **Yours to judge:** does it render, is it inside the safe area, is the file the resolution it
  claims, does the element appear on the frame the code says, do two files agree with each other,
  did the audio come back with every line in it.
- **Theirs to judge:** whether a line reads, whether a joke lands, whether a metaphor holds,
  whether a scene is too busy or too slow, whether the composition is right.

The split is not about capability. It is about who the video is for.

**Check —** before calling something over-complicated, simplifying it, or building a different
version of a beat, ask whether the meaning of that beat has been agreed. If it has not, the
meaning is the conversation to have first.

Detail: [judgement.md](reference/judgement.md)

## 3 · Numbers come after the thing they measure

A duration is an estimate until the thing exists and can be watched. Then it is a measurement.

Fixed before any work starts: resolution, frame rate, whether there is sound, the safe area, the
scenes, the beats, the intent. Tentative until the thing is built: how long each part runs, how
long the whole runs, where each beat lands.

Once it is built, measure it. Changes after that are additive — polish lands on a finished cut and
the total moves a few seconds either way. That movement is the result of the work, not a problem
to fix.

Measure against something that can be played: a recorded voice, a performance, a beat on screen.
A target length cannot be played, and work aimed at one produces edits that serve arithmetic
rather than the video.

**Check —** before writing a number into a document, ask whether the thing it describes has been
built and watched. If not, the number is provisional and says so.

Detail: [timing.md](reference/timing.md)

## 4 · Drop a constraint you cannot source

A rule invented while working, then defended through a failure, is the most expensive kind of
mistake. It is invisible, it looks like care, and every attempt to work around it costs another
attempt.

**Check —** when a second attempt fails the same way, list the constraints in play and mark which
ones the person actually set. Refine only those.

## 5 · Report what happened, at the time it happened

Say a file is written after writing it. Say a check passed after running it.

Where something was not done, not verified, or not finished, say so in the same plain voice as
everything else. A report that reads as complete work will be read as complete work, and it is the
only account of the work the person has.

**Check —** before saying a thing is done, find the result that did it.

## 6 · Write so the next reader needs no memory

A note that says what not to do only works for someone who already knows what was tried. State
the rule and the reason together, in terms that make sense to someone reading it for the first
time.

This works: *"Torn edges read as handmade, cut edges read as machine-made. Keep hands torn and
keep interface elements cut — it does the work narration would otherwise do."*

This asks the reader to want something, then refuses them: *"Do not change this back to the
other value."*

Where a warning is genuinely needed — a value that looks wrong and is correct — keep it, and
explain the mechanism rather than the argument that produced it.

**Check —** read the note as someone who arrived today. If it only makes sense as a reply, rewrite
it as the rule.

Detail: [writing.md](reference/writing.md)

## 7 · Use the words already in use, and define them once

A word invented mid-task spreads into everything written after it, and the next reader meets it
with no definition. A word that already means something else in the same project is worse, because
it reads as understood.

Before a new term goes into a filename, a heading or a constant: search for it, check it is not
already taken, and if it is genuinely new, define it in one sentence where it first appears —
including when it looks obvious.

A memorable phrase that compresses a real lesson is the worst case. It travels faster than the
lesson and turns out to be false when read literally. Say the thing plainly instead.

**Check —** before introducing a noun, search the project for it. Coining a term is a decision,
not a convenience.

Detail: [writing.md](reference/writing.md)

## 8 · Intent at the head, measurements at the foot, dated

In a storyboard, a script or a plan, the top holds what was settled before the work started, plus
the tentative scope marked as tentative. What has since been measured, decided or rejected is
appended, with the date.

Editing a measured figure up into a heading causes two problems. The document starts to read as
though the measurement came first and the work was made to fit it, which is not how it happened
and misleads anyone using the document as a model. And the figure goes stale quietly, because a
number in a heading is a number nobody re-checks.

Appended notes do not have this problem. They carry their own date, they sit under the text they
replace, and the replaced text stays readable as the record of what was thought before.

**Check —** before editing a figure into the head of a document, ask whether it belongs at the
foot with a date instead.

Detail: [writing.md](reference/writing.md)

## The checks, in the order they come up

| When | What to check |
| --- | --- |
| Before starting anything long | Which sentence asked for it |
| Before judging a beat | Whether its meaning has been agreed |
| Before writing a number down | Whether the thing exists and has been watched |
| After a second attempt fails the same way | Which constraints the person actually set |
| Before reporting | Which result backs each claim |
| Before saving a note | Whether a first-time reader can use it |
| Before introducing a word | Whether it is already in use here |
| Before editing a document's head | Whether the figure belongs at the foot, dated |
